# Structured interpretation — phases 1 and 2

Opt in explicitly with `POST /api/plan-watch?mode=interpretation.v1` and JSON
`{"request":"Tiens-moi informé des actualités de Jannik Sinner.","language":"fr"}`.
Language may be `en`, `fr`, `mixed`, or `und`; omitted means `und`. It is a hint,
never a source-language or geographic constraint. The original request is kept
unchanged, including whitespace. Limits: 500 UTF-16 code units, one AI request,
15-second deadline, bounded response/schema. The endpoint uses the existing
`OPENAI_API_KEY` and `OPENAI_MODEL` configuration. No UI calls this mode.

Successful responses have `mode`, `status` (`interpreted`, `ambiguous`, or
`unresolved`), `executable:false`, `capabilityStatus:"not_assessed"`, and an
`interpretation`. This is meaning extraction, never capability approval. No
source discovery, Watch persistence, membership resolution, matching, scheduler
or notification occurs. Legacy requests without `mode` keep their old response.

## Contracts

`src/js/watch-interpretation.js` defines strict JSON schemas and bounded runtime
validation; the adjacent `.d.ts` supplies types. All fields are required; use
empty arrays/null where appropriate. Unknown fields and enum values fail closed.
Original wording is attached by the server rather than generated by the model.

Individual subjects retain names intact. Open groups retain membership criteria;
their `members` are named examples, not an exhaustive roster. Closed groups have
explicit individual members. A bounded condition graph uses unique IDs and
AND/OR/NOT nodes or typed predicates. `news_about` takes one subject; independent
subjects use OR. `mentions_together` and `relationship` are distinct. Currency
numeric subjects are ordered base/quote; decimal amounts are strings, with
French commas normalized to dots. Only GBP/EUR canonical codes are represented
in this first version; other identification remains unresolved.

Evidence uses JSON-pointer paths and exact original-text slices, indexed in
JavaScript UTF-16 code units with an exclusive end. Labels must be grounded;
membership, condition, topic, temporal/geographic and unresolved fields need
evidence. Validation rejects missing references, cycles, excessive depth,
unreachable conditions, obvious logical/numeric contradictions, unsupported
fields, changed numeric amounts, known comparison mismatches, and explicit
negative qualifiers that disappear. These checks do not prove complete semantic
fidelity or factual group membership. Model output remains untrusted.

`MonitoringPlanV1` defines only a future boundary: `not_assessed` and
`executable:false`. There is no compiler or executable plan contract yet.

## Failures and compatibility

Errors are sanitized: `INVALID_INTERPRETATION_REQUEST` (400),
`INTERPRETATION_FAILED` (502), `AI_SERVICE_UNAVAILABLE` (503), and `AI_TIMEOUT`
(504). No fallback query, implicit clarification call, or retry occurs. An
ambiguity is a successful extraction needing clarification, not a provider error.

Provider transport is shared with the existing clarification service; its
legacy prompt, schema, model fallback, response contract and currency shortcut
are retained. No existing Watch is reinterpreted. No changes are made to parser,
currency evaluation, aliases, saved definitions/queries, databases, auth,
baselines, ledgers or notifications. Opt-in output cannot be used directly by
current persistence. Phases 3 onward require separately approved capability and
version-aware persistence work.

## Focused verification

Run `NODE_ENV=test node --no-maglev --test server/watch-interpreter.test.js
server/watch-planner.test.js server/plan-watch-api.test.js
server/request-clarification-api.test.js` (one shell command).
Fixtures cover the four consumer requests, bilingual/mixed language, groups,
OR/co-occurrence/collaboration, currency, constraints, malformed output,
injection, outages and deadlines. All AI responses are mocked. This does not
establish live-model accuracy or make the four requests work in the public UI.
